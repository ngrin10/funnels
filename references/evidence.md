# Check the facts before shaping the screen

## Make a source list

Name what was read, its date or version, and what it supports. List what was not read. If the live screen cannot be reached, mark the supplied image as a stand-in. Never call a design live because it looks finished.

For calls, record the date and speaker when allowed. Use the project's private citation rules. Do not publish raw transcripts or private links in the public skill.

## Walk the path

Read the flow for each group or plan that matters. Record the route, copy, actions, next step, visible states, and events that were actually checked. Stay within the user's read/write scope.

Compare:

- The live flow with the current spec.
- The live flow with the design.
- The entry promise with checkout, delivery, and first use.

List what already exists, what is missing, and what differs. Change only the missing or wrong parts in scope. Do not rebuild an existing feature because an old doc failed to mention it.

## Map what the screen needs

| Change / visible item | What must be true | Input and source | Exists now? | Missing work and owner | What happens when missing |
|---|---|---|---|---|---|

Include each number, status, recommendation, button, and promised action. If a button needs an API or permission that does not exist, name that dependency. Do not design a working promise over a missing system.

Find shared dependencies. A missing input may block several changes; fixing it can come before the screens. Distinguish ready inputs, built but off, missing data, and missing systems. Ask about conflicts rather than assuming the newest-looking doc wins.

## Check promises and conflicts

Keep both sources and dates when prices, terms, limits, event names, or rules disagree. Name the person who can settle the issue. Do not average them or pick the nicer number.

Check that sample data is labeled, computed totals add up, comparisons use a fair base, and shown states match their rules. Do not show an estimate as a measured result or use a benchmark as this person's result.

New data pulls belong in the private data folder with `what`, `pulled`, source, account, dates, group rules, units, and known limits. Do not save raw sensitive rows when group totals can answer the question. A source fact can be added to the product notes only with its date and evidence label.

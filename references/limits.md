# Know the limits

Run this check at the start and again when the task changes.

## What this skill can do

Sort supplied facts. Find empty fields and conflicts. Ask clear questions. Map a flow. Draft a spec, screen brief, copy, and build prompt. Check whether the docs agree. Show what a builder needs to prove.

These jobs do not make the AI an expert in the product, its data, or its industry.

## What needs more help

| Task | Why this skill alone is not enough | What to get |
|---|---|---|
| Explain why a result changed | Many things can change one number at once | The data definitions, dates, change log, and a skill in the right field |
| Choose or judge a test | A small or uneven group can mislead | A test-design skill and the needed data |
| Change tracking or join data | Wrong ids, dates, or event rules can change the answer | An analytics skill, the data rules, and sample checks |
| Give advice on ads | A funnel spec does not teach paid media | A paid-media skill with the user's current rules and data |
| Set price, forecast profit, or pick a money plan | Costs, cash timing, refunds, and delivery matter | An offer or finance skill and checked inputs |
| Approve health, legal, privacy, or security rules | A polished draft cannot grant approval | The project's rules and the right qualified person; a skill can help prepare questions |
| Build in a tool or codebase not understood | A generic plan may miss real rules | A skill for that tool, its docs, and the current code |

Do not load all of these by default. Get help only for the part of the task that needs it. A narrow label fix does not need a business audit.

## Check the skill library

Use the host's available skill list. Read the exact relevant skill before relying on it. Check that it covers this job and is current enough. A skill with a matching title may still lack the method needed. State its name and what it will help with. Do not claim to have read or loaded it if access failed.

If no suitable skill is available, say what kind is needed. Do not invent an installed skill, a file path, or a tool. Ask the user for the skill or the right expert. Keep doing the parts that do not depend on it.

A skill adds a method. It cannot supply missing facts or prove a cause. Both the right method and the needed evidence must be present.

## Say the gap in plain words

Use this shape:

> I can do <part I know how to do>. I don't know <missing fact or method>. To do <blocked part> well, I need <specific input, skill, or expert>. This blocks <decision>. I can still do <safe next step>.

Example:

> I can show that fewer people bought. I don't know why yet. I need the same date range, the group rules, and a log of what changed. I also need a skill that can test the likely causes. I can still write the draft and mark that answer as unknown.

Ask one to three questions that would change the decision. Explain why each matters. Do not list every possible variable to sound thorough.

## Push back when the answer would require a guess

- A change in a number does not prove that a screen caused it.
- A sample result may not describe the whole group.
- Missing data is not zero.
- A claimed result is not a checked result.
- A skill score is not proof that a change will work.
- A user saying "just guess" does not make a sensitive fact known. Offer a clearly marked mock, a range from supplied inputs, or an open item instead. Do not use a mock to make the real decision.

If the method, evidence, or access is missing, mark the affected result `NOT KNOWN`. If the task is beyond the available skills, mark it `NEEDS SKILL`. State exactly what would let the work continue. Never claim that all causes have been ruled out without a check that supports that claim.

## Handle sensitive data with care

Ask which data may be read, stored, joined, and shared, and where. Reuse rules already given. Request the smallest useful sample or group total. Keep raw personal answers out of event names, URLs, screenshots, public examples, and build prompts unless the project's rules and user scope allow them. Redact exports before sharing.

Do not assume that a safe home for one kind of data is safe for another. If the rules are missing, stop the affected data work and ask. A spec may describe the needed check while that answer is pending.

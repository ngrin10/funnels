# Screen brief and design review

Inspect the live screen or code first. If access is missing, label the screenshot or sketch as a stand-in. Do not present an old frame as today's product.

Fill a brief per change:

- Person and moment: who arrives, from where, with which goal or concern.
- Job: the one useful action and what happens after it.
- Current screen: route, evidence/date, working parts, gap.
- Next screen: content order, main action, secondary actions, behavior.
- System: current components, fonts, colors, spacing, icons, shell, and responsive rules.
- Data: each displayed value's source, format, loading and missing-data behavior.
- States: default, loading, empty, error, success, disabled, long text, repeat visit, back and refresh. Mark unused states with reasons.
- Accessibility: labels, keyboard path, focus, reading order, contrast, zoom, reduced motion, error announcement.
- Proof: preview or frame link and the acceptance checks it covers.

Reuse the product's style when improving an existing flow. For a new product, propose a direction with a reason. Do not ban a font, force a gradient, or vary the style just for novelty.

Keep each section useful. Show the action first, supporting detail nearby, and secondary detail lower down. Use real approved content or clearly marked sample data. Keep internal event names, metrics, and task notes outside customer screens.

Check the smallest supported phone, tablet, desktop, long copy, keyboard, and zoom. Record what was actually inspected. If the design tool is unavailable, deliver the brief and mark visuals as not drawn. Do not invent frame links.
